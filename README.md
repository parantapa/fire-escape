# Fire-ESCAPE

A framework for creating high-performance wildfire spread simulators.

Fire-ESCAPE defines the "Forest Fire Simulation Language" (FFSL).
Wildfire spread simulators are described using FFSL.
FFSL model files have an extension of `.ffsl`.
The Fire-ESCAPE simulator `ffsc` can be used to compile
a wildfire spread model writen in FFSL
to high performace parallel simulators.

The current version allows for creating
parallel shared memory C++ simulators
that uses OpenMP for multi-threading.

## Installation

Requires Python 3.13 or later.

```
pip install .
```

This installs the `ffsc` command line tool.

## Usage

### 1. Compile a model to a C++ project

```
ffsc compile -i examples/example1.ffsl -o build/sim
```

This writes three files into the output directory:

* `simulator.cpp` - the generated simulator.
* `CMakeLists.txt` - the CMake build definition.
* `conanfile.py` - the Conan recipe listing the C++ dependencies.

### 2. Build the simulator

```
cd build/sim
conan build . --build=missing
```

The generated recipe uses `cmake_layout`,
so with a single configuration generator
the executable is written to `build/<build_type>/simulator`
underneath the project directory,
for example `build/Release/simulator`.

### 3. Run the simulator

```
build/Release/simulator \
    --num-ticks 100 \
    --num-rows 4096 \
    --num-cols 4096 \
    --tile-file tiles.h5 \
    --seed-file seed.h5 \
    --tick-file ticks.parquet \
    --output-file output.h5
```

Every `config` declared in the FFSL source
also becomes a command line flag,
so `config base_ember_rate` can be overridden with `--config-base-ember-rate 0.9`
without recompiling.

The `--seed` flag sets the RNG seed.
A negative value, which is the default, draws a fresh seed from the system.
The effective seed is echoed at startup,
and it is saved as the `seed` attribute of the `runstats` group in the output file,
so a run can be repeated from its own output.

Reproducibility holds for a fixed thread count.
Two single threaded runs with the same seed produce identical output
and an identical `log_prob`.
Runs that use different thread counts diverge,
because the work schedule decides which thread draws which sample.

## The FFSL language

A source file is made up of six kinds of top level declarations.
See `examples/example1.ffsl` for a complete example.

### `option`

Compile time integer constants
that determine the shape of the generated code and its memory allocation.

| Option | Default | Meaning |
| --- | --- | --- |
| `max_jump_x` | 1 | Maximum ember jump distance along rows. |
| `max_jump_y` | 1 | Maximum ember jump distance along columns. |
| `max_ember_count` | 100 | Cap on embers generated by a single tile in a tick. |

The compiler also accepts `chunk_size_x` and `chunk_size_y`,
which must be at least `max_jump_x` and `max_jump_y` respectively.
They are validated but currently unused,
and setting them has no effect on the generated code.

### `config`

Run time scalar parameters with a default value.
Each one becomes a `--config-*` command line flag on the generated simulator.

```
config base_ember_rate: float = 0.7
```

### `tick-data`

Per tick global state, read from a Parquet file at startup.
Each declared name becomes a column in that file,
and exactly one variable must carry the `key` annotation
to identify the tick index column.

```
tick-data:
    wind_speed: float
    wind_direction: float

    tick: int key
```

Tick variables are visible as ordinary globals inside FFSL functions
and resolve to the value for the current tick.

### `tile-data`

Per tile state, one value per grid cell.
Annotations control how each variable is handled:

* `seed` - read from the seed file rather than the tile file.
* `save` - written to the output file once per tick.

Exactly one variable must have type `fire_state`;
it holds the `Unburned`, `Burning`, or `BurntOut` status of the tile.
The variable of type `position` is synthetic
and is not read from any input file.

```
tile-data:
    burn_time: float
    fuel: float
    moisture: float

    pos: position
    state: fire_state seed save
```

### `fire-model`

The eight expressions that define the dynamics.
Each takes tile arguments (`t` for a tile, `s` and `d` for source and destination)
and returns either a probability distribution or a scalar expression.

| Clause | Result | Role |
| --- | --- | --- |
| `create-embers(t)` | `poisson[rate]` | Embers thrown by a burning tile this tick. |
| `ember-jump-likelihood(s, d)` | weight | Unnormalized weight of an ember landing on `d`. |
| `ember-death-prob(s, d)` | probability | Chance an ember dies in flight. |
| `ember-ignition-prob(t)` | probability | Chance a single received ember ignites `t`. |
| `create-flames(t)` | `deterministic[v]` | Flame intensity emitted by a burning tile. |
| `flame-spread-weight(s, d)` | weight | Fraction of flame passed to a neighbor. |
| `flame-ignition-prob(t)` | probability | Chance a unit of received flame ignites `t`. |
| `burn-time(t)` | `normal[mean, std]` | Ticks a tile stays `Burning`. |

### `def`

Plain functions used to keep the model expressions readable.
The language supports `int`, `uint`, `float`, `bool`,
sized variants (`i8` through `i64`, `u8` through `u64`, `f32`, `f64`),
plus the domain types `position` and `fire_state`.
Statements are limited to assignment, compound update, `if`/`elif`/`else`, `pass`, and `return`.

```
def ember_creation_rate(fuel: float, moisture: float) -> float:
    moisture_factor: float = exp(-2.0 * moisture)

    return base_ember_rate * fuel * moisture_factor
```

Blocks are delimited by indentation, as in Python.

Division follows Python rather than C.
The `/` operator always produces a `float`,
so `1 / 2` is `0.5` and not `0`.
A function that returns an `int` therefore cannot return a division directly,
and `n /= 2` is rejected when `n` is an `int`.
Every function must return on every path,
so an `if` without an `else` is not enough to satisfy a declared return type.

Three builtins are available:
`exp(float)`,
`distance(position, position)`,
and `alignment(position, position, float)`,
which projects the direction from one tile to another onto a given heading.

## Simulation model

Each tick executes the following phases,
all of them parallel loops over the grid:

1. **Create embers.**
   Every `Burning` tile samples a count of embers
   from the Poisson distribution given by `create-embers`,
   clamped to `max_ember_count`.
2. **Create flames.**
   Every `Burning` tile emits the flame intensity given by `create-flames`.
3. **Compute jump distribution.**
   For each ember source,
   `ember-jump-likelihood` is evaluated over the
   `(2 * max_jump_x + 1) x (2 * max_jump_y + 1)` neighborhood,
   and the weights are compiled into an alias table for constant time sampling.
4. **Assign embers.**
   Each ember samples a landing tile from the alias table
   and survives the flight with probability `1 - ember-death-prob`.
5. **Assign flames.**
   Flame is distributed to the eight adjacent tiles,
   scaled by `flame-spread-weight`.
6. **Ignition.**
   An `Unburned` tile that received embers or flame ignites with probability
   `1 - (1 - p_ember)^n_embers * (1 - p_flame)^n_flame`.
   On ignition its burn time is drawn from `burn-time`.
7. **Transition.**
   Tiles whose burn time has elapsed become `BurntOut`.
8. **Count states.**
   Per tick tallies are reduced across threads.

## Input and output files

**Tile file (HDF5).**
One two dimensional dataset per non-seeded tile variable,
shaped `(num_rows, num_cols)`, named after the variable.

**Seed file (HDF5).**
Same layout, but holding the tile variables marked `seed`.
This is the initial condition, including which tiles start out burning.

**Tick file (Parquet).**
One row per tick,
one column per tick variable,
with the `key` column giving the tick index.
Rows outside `[0, num_ticks)` are ignored.

**Output file (HDF5).**

* One dataset per tile variable marked `save`,
  shaped `(num_ticks, num_rows, num_cols)`,
  written incrementally as the run proceeds.
* Per tick summary series:
  `num_unburned`, `num_burning`, `num_burnt_out`,
  `num_ember_gen_sum`, `num_ember_recv_sum`,
  `num_flame_gen_sum`, `num_flame_recv_sum`.
* A `runstats` group holding the total allocation size,
  the run log probability,
  wall clock durations for each program phase,
  and a per thread, per tick duration dataset for each simulation phase.
